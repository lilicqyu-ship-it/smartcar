## 1. 症状与根因

### 1.1 症状

| 症状 | 用户感知 |
|---|---|
| 按下方向按钮后小车延迟启动 | "按钮不灵敏"，典型滞后 150–400 ms，偶发 1–2 s 完全无响应 |
| 松开按钮后小车缓慢滑行减速 | "刹不住/发肉"，最坏 ≈1 s 才停稳 |
| 首次打开控制页时整机"卡死"一下 | 页面 2 KB HTML 走 AT 通道逐字节透传期间，所有控制停摆 |
| 状态数字（`#x` 区域）刷新忽快忽慢 | 心跳应答被排队，到达时间抖动大 |

### 1.2 一次按键的时延解剖（现状链路）

以"按下 UP"为例，静态推算各段耗时（115200 bps，手机每 50 ms 轮询一次心跳）：

| # | 环节 | 位置 | 耗时（典型/最坏） |
|---|---|---|---|
| 1 | 手机 fetch `/api/forward` 发出 | — | 1–5 ms |
| 2 | esp-at 收 TCP → `+IPD` 透传 UART | — | 3–10 ms |
| 3 | **CPU2 排队**：上一条心跳请求还在走完自己的 AT+CIPSEND 会话（约 300 B 串行时间 ≈ 26 ms + 2 次 AT 往返等待） | `wifi_at.c:575-716` 单线程超循环 | **典型 25–50 ms；最坏等一个 2 s 的 CIPSEND 超时** |
| 4 | 本条请求自己的 HTTP 应答会话（先出完才能轮到下一条） | `wifi_at.c:344-395` | 40–60 ms |
| 5 | xcore 命令队列 → CPU0 控制任务节拍 | `Cpu0_Main.c:112`（10 ms tick） | 0–10 ms |
| 6 | CPU0 → CPU1 目标发布 | 10 ms tick | 0–10 ms |
| 7 | 斜坡启动：`MAX_STEP=2`/ms，占空比从 0 爬升 | `motor_algo.h:20` | **可见运动约 100–200 ms 后才可辨** |

**合计：按下→车轮转动，典型 150–250 ms，最坏秒级。** 松开→停稳更糟：fetch（同上 150–400 ms）+ 心跳超时兜底 100 ms + 对称斜坡降速 500 ms（从满速 1000 ÷ 2/ms）≈ **最坏 1 s**。

### 1.3 五个根因

1. **每个 HTTP 请求都要付一次完整 AT 协议会话税**：`AT+CIPSEND` → 等 `>`（≤2 s）→ 发数据 → 等 `SEND OK`（≤2 s），全部是 CPU2 上的同步阻塞串行往返（`wifi_at.c:86-91,344-395`）。AT 链路本身是半双工请求-应答式的，吞吐上限被协议往返次数而不是波特率决定。
2. **20 Hz 心跳轮询与控制命令挤同一条独木桥**：CPU2 超循环一次只能服务一个请求；心跳每 50 ms 一发，命令永远在排队（§1.2 #3，**这是"按钮不灵敏"的第一元凶**）。前端 `setInterval` 不等上一次 fetch 返回，响应一旦 >50 ms，浏览器并行 fetch 堆积（HTTP/1.1 每主机 6 连接上限），延迟雪球式放大（`wifi_at.c:211`）。
3. **CPU2 是"阻塞到底"的超循环**：`TIME_INFINITE` 写（`wifi_at.c:90`）、逐字节 1 ms 轮询读、读消息 500 ms 超时——任何一个环节慢，整机输入输出一起慢。TC275 的三核里最忙的居然是跑通信的这颗，而它 100% 的时间都耗在"等"上，**没有做任何真正的计算**。
4. **对称斜坡太保守**：加减速都是 2/ms（0.5 s 满程）。安全上合理，但启动像油车怠速起步、停止像溜车，直接吃掉体感的一半。
5. **前端缺移动端基本处理**：无 `touch-action:none`（长按/滑动会触发浏览器手势与上下文菜单，`pointercancel` 把 `onpointerup` 吞掉 → 手指没松开小车却停了，或反过来 stop 丢失）；无 `user-select:none`；STOP 是 `onclick`（要点一下才触发）。

另有一个结构性风险：页面 HTML（约 1.3 KB）与所有应答共用 1536 B 栈缓冲 + 115200 bps 通道（评估报告 P0-2/P2-1），首次打开页面 ≈200 ms 内控制链路冻结。

## 2. 方案总览

**推荐方案（Track B）：把"网络"整体搬进 ESP32-C6，把"字节流"还给 TC275。**

一句话：C6 刷自研固件，从"AT 透明猫"升级为**网络协处理器**——自己跑 softAP + WebSocket 服务器 + 静态页面；C6 与 TC275 之间换**全双工、帧式、无往返的 2 Mbps 二进制流**；TC275 侧 CPU2 从"阻塞 AT 会话机"变成"非阻塞帧泵"。**安全模型一行不改**（心跳超时、CPU1 失联看门狗、急停旁路、斜坡限幅全部保留）。

```
【现状】                                    【目标 Track B】
手机 ──HTTP── esp-at(AT翻译层)              手机 ──WebSocket── C6 自研固件(HTTPD+WS服务器)
              │ 每请求一次AT往返+应答                        │ 无翻译层，直接收发
              ▼ 115200, 半双工阻塞                          ▼ 2 Mbps, 全双工帧流
        TC275 CPU2 阻塞超循环                         TC275 CPU2 非阻塞帧泵(<5%负载)
              │ 命令队列                                    │ 同一套 AA55 协议(零改动)
              ▼                                             ▼
        CPU0(10ms) → CPU1(1kHz)                       CPU0(10ms) → CPU1(1kHz, 双斜率)
        安全模型保持不变                               安全模型保持不变
```

为什么这叫"释放两个板子的极致性能"：

| 板子 | 现状 | 目标 |
|---|---|---|
| ESP32-C6（160 MHz RISC-V, Wi-Fi 6, 512 KB RAM, 8 MB flash） | 只做 AT 翻译，CPU 占用 <5%，8 MB flash 只用来放 AT 固件 | 跑 HTTPD + 多客户端 WebSocket + 页面静态资源（gzip 后 <15 KB 放 flash，毫秒级加载）+ Captive Portal + 链路守护；CPU 占用 <15%，**网络能力从 115200 半双工变成 >10 Mbps 级** |
| TC275（3×200 MHz） | CPU0 负载 ~5%；CPU1 ~2%；CPU2 名义 100% 实际全在阻塞等待 | CPU2 变非阻塞泵后 **<5% 真实负载**，腾出来做链路鉴权/OTA 转发/加密；CPU1 双斜率 + 为 V1.1 编码器 PI 预留 85% 空闲；CPU0 预留遥测融合/IMU。**三核第一次同时"活着"** |

体验指标承诺（§5 有完整预算表）：**按下→动 < 50 ms（现状 150–400 ms）；松开→停 < 100 ms（现状最坏 1 s）；遥测 50 Hz 持续流（现状按需拉取）；页面加载 < 100 ms（现状 ≈200 ms 且阻塞控制）；支持 1 控制端 + 2 观赛端（现状 1 客户端独占）。**

## 3. Phase 0：立即止血（0.5–1 天，不动架构，独立可交付）

在做 Track B 之前，以下改动先落地，立刻把"最难受"的部分消掉，且全部是 Track B 的子集，不做无用功：

1. **前端（改 `wifi_at.c` 里的页面字符串 + JS）**：
   - 全局 `touch-action:none; user-select:none; -webkit-user-select:none`，`contextmenu` 屏蔽；
   - `pointerdown/pointerup/pointercancel/pointerleave` 四事件齐全，`setPointerCapture`，任何异常路径都发 stop；
   - **停掉 50 ms setInterval 轮询，改为"按住即驾驶流"**：手指按住期间以 80–100 ms 间隔递归 `await fetch('/api/move?dir=X&speed=Y')`（上一次返回才发下一次，杜绝堆积），松开发一次 `/api/stop`。心跳语义由 move 流本身承担（现 100 ms 心跳超时天然兜底），请求数直接减半；
   - STOP 改 `onpointerdown` 立即触发。
2. **斜坡改双斜率（`motor_algo.c/h`）**：加速保持 2/ms；**减速（向零）放宽到 10/ms（100 ms 停稳）**；急停立即刹车路径不变。松开"发肉"感立刻消失。
3. **CIPSEND 超时从 2 s 砍到 300 ms，失败即放弃本条应答**（`wifi_at.c:365,377`）：单次卡顿上限从 2 s 降到 0.3 s；顺带把 `TIME_INFINITE` 写改为有限超时（评估报告 P2-1）。
4. **心跳轮询周期 50→100 ms**（若暂不做驾驶流）：CPU2 队列压力减半。

Phase 0 后预期：按下→动 ~100–150 ms，松开→停 ~150–200 ms，秒级冻结消失。**受限于 AT 往返税，这就是 esp-at 架构的天花板，剩下的只有 Track B 能解。**

## 4. Track B 详细设计

### 4.1 ESP32-C6：从"猫"到网络协处理器

刷自研 ESP-IDF 固件（替换 esp-at；现有 `../esp-at` 构建环境直接复用 IDF 工具链）。单任务 + HTTPD 事件模型即可，组件划分：

| 组件 | 职责 | 资源预算 |
|---|---|---|
| `app_wifi` | softAP（SSID/密码存 NVS，可配）+ Captive Portal DNS（`53/udp` 野答 → 手机连上即弹页） | RAM ~30 KB |
| `app_httpd` | `GET /` 与静态资源（gzip 后存 flash 的现代化控制页）；`/ws` 升级 WebSocket | 每客户端 ~12 KB，限 3 客户端 |
| `app_ws` | WS 会话管理：**唯一**标注一个控制端（第一个发 `CLAIM` 的客户端），其余为只读观赛端；控制端心跳/驾驶流超时检测 | — |
| `app_uart` | 与 TC275 的帧链路（§4.2）：RX 中断 + 环形缓冲，TX 队列非阻塞发送 | 2×1 KB 缓冲 |
| `app_bridge` | 双向翻译：WS 二进制消息 ↔ UART 帧；**透传不解析语义**（安全判定全部留在 TC275） | — |
| `app_ota`（P2） | 自身固件 OTA | — |

C6 新增的**主动性**（现状完全没有的能力）：

- **断链即报**：TCP/WS close 或控制端驾驶流超时，C6 **毫秒级**主动向 TC275 发 `LINK_DOWN` 帧 → CPU0 立即清目标，不再等 100 ms 心跳超时；
- **遥测广播**：TC275 发布的 50 Hz 遥测由 C6 广播给所有在线客户端（现状 GET_STATUS 每次都要付一次请求税）；
- **连接质量**：C6 周期发 PING 给 TC275 回传，RTT 直接显示在手机页面上。

### 4.2 C6 ↔ TC275 高速二进制链路

- **物理层**：沿用 P15.0/P15.1（ASCLIN1），波特率 **115200 → 921600 起步、2 Mbps 目标**（ASCLIN @200 MHz 与 C6 UART 都远超此能力；杜邦线先验证 921600，短线/排线可上 2M。两端波特率做成帧内可配 + NVS 保存）。
- **帧格式：直接复用现有 `AA 55 CMD LEN DATA CRC` 协议**——这是本方案最大的省力点：TC275 侧 `PROTO_feedByte`/`PROTO_sendBytes` 一行不改，`protocol.c` 的全部命令语义（含 0x32 急停旁路）原样生效。
- **新增帧**（不与 0x01–0x40 冲突）：

| CMD | 方向 | 含义 |
|---|---|---|
| `0x41 TELEMETRY` | TC275→C6 | 50 Hz 状态帧（= 现有 `ProtocolStatus` 6 B + STM 时间戳 4 B），C6 广播给 WS 客户端 |
| `0x42 LINK_STATE` | C6→TC275 | 1 B：0=无客户端 / 1=有观赛 / 2=控制端在线；变 0 时 CPU0 按通信故障处理 |
| `0x43 PING/PONG` | 双向 | RTT 测量，页面显示 |
| `0x44 BAUD_REQ/ACK` | C6→TC275 | 握手升速（Phase 3） |

- **流量核算**（2 Mbps = 200 KB/s）：下行控制 30 Hz × 12 B ≈ 0.4 KB/s；上行遥测 50 Hz × 16 B ≈ 0.8 KB/s；**链路占用 <1%**——对比现状每次交互 300 B×串行往返，这是两个数量级的释放。

### 4.3 TC275 侧：三核重新排布

**CPU2（改动最大，价值也最大）——阻塞会话机 → 非阻塞帧泵：**

- RX：保留 iLLD 中断收包进环形缓冲（现状已是），超循环只做"从环取字节 → `PROTO_feedByte`"，**任何函数不再有毫秒级阻塞**；
- TX：`XCORE_cmdPush` 之外的发送（遥测转发、AT 时代的应答逻辑全部删除）改为"应用层写队列满即丢遥测帧"（遥测允许丢帧，命令不允许——命令路径只有 C6→TC275 单向）；
- 增加 1 ms 心跳式巡检：命令队列、链路状态、日志环服务；
- 结果：CPU2 真实负载 <5%，剩余算力留给帧鉴权（HMAC/token 校验，接评估报告 P3-5）与 OTA 转发。

**CPU0：**
- 控制任务保持 10 ms（占时延预算 0–10 ms，不是瓶颈；后续可选：CPU2 置共享标志 + GPSR 软件中断即时唤醒，再削 5–9 ms，列为可选项）；
- 新增：处理 `LINK_STATE`/`TELEMETRY` 发布（把现有 10 ms 一次的 `XCORE_statusPublish` 加时间戳交 CPU2）；处理断链事件与现有心跳超时**双保险并存**。

**CPU1：**
- 双斜率斜坡（Phase 0 已做）；增加"斜坡档位"帧（ECO/SPORT：加速 2 或 6/ms），给用户"运动模式"的爽感开关；
- 1 kHz 循环目前 CPU 占用 ~2%，为 V1.1 编码器闭环（1 kHz PI + 堵转检测）预留充足余量——这是"极致性能"的真正去处。

### 4.4 手机端 Web 应用（"惊艳"的主体）

页面从 `wifi_at.c` 字符串迁移为 C6 flash 里的 gzip 静态资源（现代浏览器，无兼容包袱）：

1. **虚拟摇杆**（替代四个方向键）：手指位置 → 绝对速度向量 `(v, ω)` → 差速公式 `left = v - ω, right = v + ω` 钳位后随**驾驶流**以 20–30 Hz 下发；全向、比例控制，手指在哪车就往哪走；
2. **驾驶流**（§3 Phase 0 模式保留）：按住即流、松开即停、断流即停——与 100 ms 心跳超时天然闭环；
3. **实时仪表**：50 Hz 遥测驱动——左右轮速度条（CPU1 实际输出，不是目标值）、状态灯（心跳/故障码/急停）、**RTT 数字**、链路速率；
4. **多客户端**：第一台手机是控制端（页面显示"遥控中"徽标），其他手机/电脑打开同页自动成观赛端（只看遥测），页面一键申请接管；
5. **Captive Portal**：连上 `AURIX-SmartDrive` 弹出控制页（零点击进入）；mDNS `mycar.local` 备用；
6. **触感**：按下/急停触发 `navigator.vibrate(10/50)`；
7. **游戏手柄**（Gamepad API，零成本加分项）。

> 诚实声明：PWA/Service Worker 需要 HTTPS 或 localhost，纯 HTTP 的 softAP 下不可用，本方案不承诺"离线缓存安装"；但页面本体 <15 KB 从 C6 flash 直接出，AP 模式加载本来就 <100 ms，无损体验。

### 4.5 安全模型：保持 + 增强

| 机制 | Track B 后 |
|---|---|
| 心跳 100 ms 超时（CPU0） | 保留（与 LINK_STATE 双保险，P0-3 的故障锁存修复不变） |
| CPU1 150 ms 失联看门狗 | 保留 |
| 0x32 急停 + CPU1 旁路位 | 保留，路径不增长（评估报告 P0-1 的竞态修复照做） |
| 斜坡/钳位 | 保留，改双斜率 |
| 新增 | C6 毫秒级断链直报；token 鉴权挂点（CPU2 有算力了）；驾驶流超时 = 心跳语义，手机断网/锁屏自动停车 |

## 5. 性能预算对比

按下→动（touch-to-move）、松开→停（release-to-stop）逐段预算（估算值，§8 给出实测方法）：

| 段 | 现状（典型/最坏） | Track B（典型/最坏） |
|---|---|---|
| 手机 → C6 | 3–10 ms | 1–3 ms（WS 二进制帧，AP 内网） |
| C6 内部 | AT 翻译 + 排队 **25–2000 ms** | <1 ms |
| C6 → TC275 | 3–10 ms（+IPD 透传） | **<0.1 ms**（16 B @2 Mbps） |
| TC275 CPU2 | 排队 + 本请求会话 40–60 ms → **0 ms**（非阻塞） | 0 ms |
| CPU0 节拍 | 0–10 ms | 0–10 ms（可选中断唤醒 0–0.2 ms） |
| CPU1 启动 | 斜坡出可见运动 ~100 ms | 同左（安全底线，SPORT 档 ~40 ms） |
| **按下→动合计** | **150–400 ms / >2 s** | **20–50 ms** |
| 松开→停合计 | 150–400 ms + 100 ms + 500 ms 斜坡 ≈ **最坏 1 s** | 30 ms（松开帧）+ ≤10 ms + 100 ms 减速斜坡 ≈ **<100 ms** |
| 遥测更新率 | 按需，受排队抖动 | 50 Hz 恒定 |
| 页面加载 | ≈200 ms（阻塞控制链路） | <100 ms（flash 静态资源，不碰控制路径） |
| 并发客户端 | 1（独占） | 1 控制 + 2 观赛 |

板级资源终态：

| 资源 | 现状 | Track B 终态 |
|---|---|---|
| TC275 CPU0 | ~5% | <10%（余量给 IMU 融合/日志） |
| TC275 CPU1 | ~2% | <15%（余量给 1 kHz 编码器 PI、档位曲线） |
| TC275 CPU2 | 名义 100%，实为阻塞等待 | **<5% 真实负载**（余量给鉴权/OTA） |
| 串口链路 | 115200，半双工会话式，单事务 300 B | 921600–2 Mbps 全双工帧流，占用 <1% |
| C6 CPU / RAM | <5% / ~40 KB（esp-at） | <15% / ~80 KB（HTTPD+3 WS） |
| C6 flash | 仅 AT 固件 | 固件 + gzip 页面资源 + NVS 配置（8 MB 用武之地） |

## 6. 实施计划

| 里程碑 | 内容 | 涉及文件 | 工作量 |
|---|---|---|---|
| **M0 止血**（§3） | 前端驾驶流/触摸修复、双斜率、超时收紧 | `Middleware/wifi_at.c`（页面字符串）、`App/motor_algo.c/.h` | 0.5–1 天 |
| **M1 C6 固件骨架** | IDF 工程建立、softAP + HTTPD + 单 WS 回环、UART 115200 帧桥（`TELEMETRY/LINK_STATE/PING` 三帧先通） | 新仓库 `esp32c6-fw/`（复用 esp-at 工具链） | 2–3 天 |
| **M2 TC275 换轨** | 新 `wifi_link.c`（CPU2 非阻塞泵）替换 `wifi_at.c`（编译开关保留回退）；`protocol.c` 零改动验证；CPU0 处理 LINK_STATE | `Middleware/`、`Cpu2_Main.c`、`Cpu0_Main.c` | 2 天 |
| **M3 Web 应用** | 摇杆 + 驾驶流 + 50 Hz 仪表 + 多客户端 + Captive Portal + 触感 | C6 flash 静态资源 | 2–3 天 |
| **M4 调速与打磨** | 921600→2 Mbps 握手、SPORT 档、RTT 仪表、token 鉴权挂点、（可选）CPU0 中断唤醒 | 两板 | 1–2 天 |

依赖关系：M1 与 M0 并行；M2 依赖 M1 的帧协议定稿；esp-at 驱动保留在编译开关后面（`USE_WIFI_AT`），M4 验收前不删，作为回退路径。

## 7. 风险与回退

| 风险 | 等级 | 缓解 |
|---|---|---|
| 2 Mbps 在杜邦线上误码 | 中 | 默认 921600；`BAUD_REQ/ACK` 握手 + CRC 失败率统计自动降速；正式版改排线/缩短走线 |
| C6 自研固件稳定性不如 esp-at | 中 | WS/UART 全部非阻塞 + 任务看门狗；C6 侧若固件挂死，TC275 的 150 ms 失联看门狗兜底停车（安全永远在 TC275，不在 C6） |
| 现有二进制协议客户端（TCP 8080 裸协议）兼容 | 低 | C6 固件可同时开 TCP 8080 直通桥（协议原样），老客户端零感知 |
| IDF 工具链/构建环境 | 低 | esp-at 构建已验证过 IDF 环境，直接复用 |
| 回退 | — | TC275 编译开关切回 `USE_WIFI_AT` + C6 重刷 esp-at 固件 = 完整回到现状；M0 的前端与双斜率改动独立于固件，回退也保留 |

## 8. 验收测试

1. **touch-to-move 实测**：手机 240 fps 慢动作拍摄"手指触屏瞬间 → 车轮首动"，逐帧计数。通过线：Track B ≤ 50 ms（≈12 帧）；Phase 0 后 ≤ 150 ms。
2. **release-to-stop 实测**：满速松开 → 车轮停转。通过线：≤ 120 ms；断链场景（开飞行模式）≤ 150 ms。
3. **遥测流畅度**：页面仪表 30 s 内更新间隔无 >40 ms 的空洞；RTT 显示稳定 <10 ms。
4. **秒级冻结回归**：连续刷新页面 20 次 + 边驾驶边刷新，任何一次控制延迟 >200 ms 即失败（现状必现）。
5. **多客户端**：手机 A 控制中，手机 B 打开页面为观赛端且遥测同步；B 申请接管后 A 变观赛端；全程无急停误触发。
6. **安全回归（不允许因优化劣化）**：急停帧 → CPU1 立即刹车路径 < 5 ms（UART 逻辑分析仪 + PWM 探针）；拔 C6 → 车按失联看门狗停；心跳/急停/斜坡全部沿用评估报告 §6 的安全用例。
7. **链路误码**：2 Mbps 下 30 min 连续遥测，CRC 错误计数为 0（或自动降速事件 0 次）。

## 9. 附：为什么不选另外两条路

- **esp-at 透传模式（AT+CIPMODE=1）**：能消掉每包 AT 往返税，把链路变成裸 TCP 字节流，TC275 的 `PROTO_feedByte` 直接受益。但浏览器无法开裸 TCP——**手机网页遥控这条路就断了**（只能配原生 App）。作为"不刷 C6 固件"场景下的备选保留，不作为终态。
- **只优化 TC275/CPU2 调度、保留 HTTP 轮询**：治不了根——AT 往返税和"请求-应答"模型是卡顿的源头，轮询型 HTTP 在 esp-at 上每请求 40–60 ms 的地板价无法突破。M0 的驾驶流改造已把请求数砍半，再往上只剩换轨一条路。

**结论：M0 先行（当天见效），Track B 分四个里程碑两周内交付，体验指标全面跨数量级，且安全模型一行不改、回退路径完整。**
