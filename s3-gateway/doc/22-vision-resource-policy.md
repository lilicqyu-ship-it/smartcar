## 1. 资源真相：空闲的是核 1 和 PSRAM，不是射频

doc/20 的分配把核 0 留给了射频/IP 面之后，核 1 的负载只有
`cam(23) > link(12) > bridge(10) > ota(8) > led(3)`——阶梯上部全是短突发，
核 1 的持续算力基本闲置；8 MiB octal PSRAM 在单观看者 + QVGA/VGA 推流下
同样有大量余量。

但**把 8 MiB 填满的路径（更高分辨率、更多观看者、`/stream` 与
`/ws/camera` 双 sink 同时满速）不触及这三个资源的瓶颈顺序**：

1. **先打爆 2.4G SoftAP**——一个 AP、半双工空口，多一路满速流直接吃掉
   控制面的空口预算（手持机控制帧跳发、RADIO LOST，10-02 台架已演示过
   视频 vs 控制上行挤兑的完整链路）；
2. **再打爆 Remote 解码**——手持机 VGA 解码 ~450 ms/帧，多出来的带宽只能
   变成对端 latest-only 丢弃；
3. **最后才碰到 PSRAM**——按 640×480 RGB565 槽（614 KB）×帧数算，填满
   8 MiB 需要的路数远超前两条墙。

结论：**扩容方向不是"把 PSRAM/核 0 用满"，而是把视觉算力放到空闲的核 1，
用 PSRAM 传指针而不是多开消耗空口的流。**

## 2. 摆放政策（约束 P4/P5/P6）

| 用法 | 放哪 | 不要做的替代（失败模式） |
|---|---|---|
| **P4** Frame Hub + line/color/QR | 核 1 `vision_task`，读 PSRAM fb 指针（Frame Hub 租约，见 §3） | 在核 0 httpd 会话里做视觉——视觉是持续算力负载，会与 WiFi/lwIP 挤占核 0，复现"控制 RTT 抖动"，且 httpd 任务栈（8K/4K）装不下算法 |
| **P5** Assist 只出高层 omega | `bridge`（核 1）经现有 SF 帧下行 | 视觉任务直接发 DRIVE——绕开 bridge 的命令泵/权限模型（ADR-008），且视觉任务崩溃会直接作用于车 |
| **P6** ESP-DL 检测 | 先做 PSRAM 预算再开（模型 + 输入缓冲 + 检测输出都记账，见 §4） | 默认 VGA 帧上盲目上检测模型——PSRAM 余量被误判，撞墙后表现为分配失败/降级而不是提前否决 |
| 手机高清 MJPEG | 维持现窗 14400 + 单观看者 503 | 双观看者抢 2 槽 fb 队列——各拿一半帧且互加延迟（doc/19 §"一次只服务一个观看者"） |

## 3. P4 执行注记：Frame Hub 在核 1

Frame Hub（LLDD §9"一次采集、多路带租约消费"）是 P3/P4 的共同前置
（doc/21 §153）。落位约定：

- Hub 本体与一切视觉消费任务在**核 1**；推流 sink（:81 httpd 任务，核 0）
  保持现在的"拿着 fb 描述符写完就还"的消费方式，或改为向 Hub 租约——
  两条路都不把算法搬进核 0。
- 视觉读的是 **PSRAM 里的 fb 指针**（零拷贝租约，`CAMERA_FB_IN_PSRAM`），
  不为视觉另开拷贝缓冲；租约超时由 Hub 回收，消费慢的视觉丢帧不影响推流。
- 视觉结果走**文本面**（`vision` JSON，doc/21 P4 行）出核 1——它和
  cam_state 一样是低频小消息，不与二进制视频流争空口。

## 4. P6 PSRAM 预算清单（开检测前的硬门槛）

在启用 ESP-DL 之前，逐项记账并写进 PR：

- 模型本体（flash/PSRAM 驻留 + 运行时张量 arena）；
- 输入缓冲（缩放后的检测输入，若从 fb 原分辨率缩放要额外一份）；
- 与推流槽数（3×VGA fb = 614 KB×2 + WS 组装 ~10 KB + MJPEG 无额外）共存
  后的**最坏同时驻留**，对照 `heap_caps_get_largest_free_block(MALLOC_CAP_SPIRAM)`
  台架实测值；
- 结论写回本文档 §2 的 P6 行（预算通过/未通过 + 数字）。

未过预算即不开——降级路径是降检测分辨率/帧率，不是挤掉推流 fb。
